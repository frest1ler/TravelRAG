# TravelRAG — туристический ассистент по городам России

Учебный RAG-ассистент для поиска достопримечательностей и генерации туристических рекомендаций на русском языке. Проект построен на модульных компонентах LangChain, Chroma, multilingual E5 и Qwen2.5 и работает по собственной базе объектов четырёх городов: Екатеринбурга, Ярославля, Нижнего Новгорода и Владимира.

Основной сценарий запуска — Google Colab с GPU. Весь исследовательский pipeline находится в ноутбуке [`travel_rag.ipynb`](travel_rag.ipynb).

## Что делает проект

Пользователь задаёт вопрос, например:

```text
Что посмотреть во Владимире?
```

Система:

1. определяет упомянутый город;
2. ограничивает поиск документами этого города;
3. строит embedding запроса с помощью `intfloat/multilingual-e5-small`;
4. извлекает релевантные документы из Chroma;
5. передаёт найденный контекст в `Qwen/Qwen2.5-1.5B-Instruct`;
6. генерирует краткий ответ, используя только сведения из контекста.

```text
Вопрос
  ↓
Определение города
  ↓
multilingual-e5-small
  ↓
Chroma + metadata-фильтр City
  ↓
Top-5 документов
  ↓
Qwen2.5-1.5B-Instruct
  ↓
Ответ туристического гида
```

## Данные

Исходный датасет содержит название объекта, город, краткое русскоязычное описание, изображение в Base64 и английское описание изображения.

В исходной таблице около 14,6 тысячи строк. Несколько строк могут относиться к одной достопримечательности, поэтому данные группируются по названию, городу и описанию. После агрегации получается около 320 объектов; точное количество после очистки зависит от результата кластеризации.

Датасет автоматически скачивается из Google Drive, если `file.csv` отсутствует:

```text
https://drive.google.com/uc?id=1P1BsvI2jPN3fEqjc2YZxmQ-MTs22WVUk
```

Изображения используются для визуальной проверки данных, а их текстовые captions — при анализе и поиске выбросов. Текущая версия RAG индексирует текстовые документы, поэтому это не полноценный мультимодальный retrieval.

## Подготовка данных

Ноутбук выполняет следующие этапы:

1. проверяет структуру и пропуски в исходном CSV;
2. агрегирует изображения и captions по достопримечательностям;
3. переводит русские описания на английский через `facebook/mbart-large-50-many-to-many-mmt`;
4. объединяет перевод с captions изображений;
5. очищает и нормализует текст;
6. строит TF-IDF-признаки;
7. анализирует кластеры KMeans и silhouette score;
8. удаляет автоматически и вручную выбранные нерелевантные объекты;
9. сохраняет промежуточный результат в `data_filterd.csv`.

После перевода mBART удаляется из памяти, чтобы освободить GPU перед построением embeddings и загрузкой генеративной модели.

## Модели и компоненты

| Компонент | Реализация |
|---|---|
| RAG-интеграция | LangChain (`langchain-core`, `langchain-chroma`, `langchain-huggingface`) |
| Перевод | `facebook/mbart-large-50-many-to-many-mmt` |
| Embeddings | `intfloat/multilingual-e5-small` |
| Векторная база | Chroma |
| Генерация | `Qwen/Qwen2.5-1.5B-Instruct` |
| Квантизация генератора | BitsAndBytes, 4-bit NF4 на CUDA |
| Предобработка | NLTK, pymorphy3, TF-IDF |
| Анализ выбросов | KMeans, silhouette score |
| Визуализация | Matplotlib, PCA, UMAP |

Qwen используется только для генерации. Embeddings строятся специализированной компактной моделью E5 с отключённым multiprocessing. Это снижает расход GPU-памяти и предотвращает зависание Colab при индексации.

RAGatouille и ColBERT в стабильной версии отключены из-за несовместимости их зависимостей с современным LangChain и Python в Colab. Retrieval выполняется непосредственно через Chroma.

## Запуск в Google Colab

1. Загрузите `travel_rag.ipynb` в Google Colab.
2. Выберите `Среда выполнения → Сменить среду выполнения → GPU`.
3. Выполните установочную ячейку.
4. Если Colab попросит перезапуск, перезапустите среду и продолжите с ячейки импортов.
5. Выполняйте ячейки последовательно сверху вниз.

Ноутбук не переустанавливает базовые библиотеки Colab — PyTorch, NumPy, Pandas и scikit-learn. Это позволяет избежать бинарных конфликтов с готовым окружением.

Первый полный запуск может занять продолжительное время, поскольку mBART переводит уникальные описания и модели скачиваются с Hugging Face. После очистки создаётся `data_filterd.csv`, который можно использовать как промежуточный результат при повторных экспериментах.

Токен Hugging Face необязателен, но помогает избежать ограничений анонимных загрузок:

```python
from huggingface_hub import login
login("YOUR_HF_TOKEN")
```

Не публикуйте настоящий токен в ноутбуке или репозитории.

## Проверка работы

После создания векторной базы должно появиться сообщение:

```text
Embedding model created
Vector database created: N документов
```

Создание индекса для нескольких сотен коротких документов не должно занимать десятки минут. Если ячейка долго не завершается, проверьте, что используется:

```python
multi_process=False
EMBEDDING_MODEL_NAME = "intfloat/multilingual-e5-small"
```

## Оценка

В ноутбуке предусмотрены:

- `City Precision@5` — доля найденных документов нужного города;
- `Hit@5` — наличие ожидаемого объекта среди пяти результатов;
- cosine similarity между embeddings вопроса и ответа как дополнительная proxy-метрика;
- сравнение результатов по городам;
- визуализация пространства документов через PCA и UMAP.

Cosine similarity вопроса и ответа не измеряет фактическую корректность и не должна интерпретироваться как полноценная оценка RAGAS.

## Результаты последнего запуска

| Показатель | Результат |
|---|---:|
| Строк в исходном датасете | 14 634 |
| Строк после удаления пропусков | 12 078 |
| Объектов после группировки | 320 |
| Документов в итоговой базе знаний | 278 |
| Время перевода корпуса | около 1 мин 23 с |
| Время создания Chroma | 7,69 с |
| Размер тестовой выборки | 100 вопросов |
| Время оценки | около 9 мин 17 с |
| Средняя cosine similarity вопрос–ответ | 0,916 |
| City Precision@5 | 1,0 для каждого города |

Значение `City Precision@5 = 1.0` показывает, что metadata-фильтрация устранила смешивание объектов разных городов. Это основной подтверждённый результат улучшения retrieval.

Полученные значения `Hit@5` составили 0,118 для Владимира, 0,074 для Екатеринбурга, 0,045 для Нижнего Новгорода и 0,059 для Ярославля. Однако текущий тест связывает общие вопросы с одним случайно выбранным объектом, хотя для таких вопросов существует много правильных ответов. Поэтому `Hit@5` в этом эксперименте нельзя напрямую считать оценкой общего качества поиска. Для более строгой проверки нужны объектно-ориентированные вопросы или несколько релевантных объектов для каждого запроса.

## Ограничения

- Корпус охватывает только четыре города.
- По Владимиру данных заметно меньше, чем по остальным городам.
- Координаты и изображения пока не возвращаются в ответе.
- Изображения не индексируются отдельной vision-моделью.
- Chroma создаётся в памяти и перестраивается после перезапуска среды.
- Reranking отключён; используется dense retrieval с фильтрацией по городу.
- Небольшая генеративная модель иногда изменяет название объекта, путает похожие названия городов или добавляет неподтверждённую формулировку.
- Автоматическое удаление наименьшего кластера требует ручной проверки: в последнем запуске оно непропорционально сильно сократило число объектов Нижнего Новгорода.
- Текущие тестовые вопросы подходят для проверки города, но недостаточно точны для строгой оценки `Hit@5`.
- Это исследовательский ноутбук, а не production API.

## Краткий итог

Проект демонстрирует полный цикл создания локального RAG-прототипа: анализ и очистку мультимодального источника, построение текстовой базы знаний, semantic retrieval с metadata-фильтрацией, локальную генерацию на GPU и базовую оценку качества поиска. Последний полный запуск подтвердил стабильное построение индекса и корректную фильтрацию результатов по городу; основными направлениями дальнейшей работы остаются фактическая строгость генерации и улучшение методики оценки retrieval.
